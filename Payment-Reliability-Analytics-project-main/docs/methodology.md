# Methodology

How this analysis is built, which definitions it uses, why particular choices were made, and what it does not claim.

> **Synthetic data.** PayPulse is fictional and every record is generated by [`../src/generate_data.py`](../src/generate_data.py). This project uses no PhonePe data and no data from any real company.

---

## 1. Pipeline

| Stage | Script | Output |
|---|---|---|
| Generate | `src/generate_data.py` | `data/generated/transactions.csv`, `data/sample_transactions.csv` |
| Validate | `src/validate_data.py` | 19 pass/fail checks; aborts the pipeline on any failure |
| Load | `src/build_database.py` | `data/generated/paypulse.sqlite` + `transaction_enriched` view |
| Analyse | `sql/01..06` via `src/run_analysis.py` | 16 CSV tables + `outputs/analysis/summary.json` |
| Report | `src/build_excel_dashboard.py` | `outputs/Payment_Reliability_Analytics_Dashboard.xlsx` |
| Verify | `scripts/excel_qa.ps1`, `tests/` | Preview PNG, QA report, 52 tests |

Orchestrated by `python src/run_pipeline.py`. Each stage is a separate process, so a failure stops the run with the failing stage's exit code.

### One source of truth for definitions

`src/config.py` holds the peak-hour window, the incident bank and dates, the scenario assumptions and the failure causes the scenarios target. `build_database.py` renders those constants into the SQL view definition, and `run_analysis.py` uses the same constants for the summary. A test asserts that the peak hours stored in the database match `config.py`, so the definition cannot drift between the generator, the SQL, the workbook and the documentation.

## 2. Business logic decisions

### `transaction_status` is the initial attempt, not the final outcome

Every row is one payment attempt. `transaction_status` records whether **that attempt** succeeded. If it failed and was retried, the retry result is recorded separately in `final_retry_outcome` (`Recovered` / `Still Failed`), and rows that were never retried carry `Not Retried`.

This was a deliberate choice. Blending retry recoveries into the headline rate would raise it by roughly 0.77 pp and hide the very thing worth managing — how often the platform fails on first contact, and how well the retry policy compensates. Both numbers are reported; neither is allowed to disguise the other.

### Success-rate denominators

- **Transaction success rate** = successful attempts ÷ **all attempts**. Attempt-weighted, so a ₹50 payment counts the same as a ₹50,000 one.
- **Value success rate** = successful payment value ÷ **total attempted value**. Value-weighted. Comparing the two shows whether failures skew towards larger payments. Here they are nearly identical (95.57% vs 95.53%), so failures are broadly value-neutral.
- **Failure rate** = 1 − transaction success rate, always reported next to the absolute failure count.

Every ratio in SQL divides through `NULLIF(denominator, 0)` so a filtered slice with no rows returns `NULL` rather than raising.

### Retry recovery

- **Retry rate** = retried attempts ÷ **all attempts** (1.75%) — the exposure of the platform to retries.
- **Retry rate of failures** = retried attempts ÷ **failed attempts** (39.42%) — retry coverage.
- **Retry recovery rate** = `final_retry_outcome = 'Recovered'` ÷ retried attempts (44.15%) — retry effectiveness.

Only failed attempts are ever retried, which `validate_data.py` and the test suite both enforce. Recovery is reported per failure cause because that is the only cut that supports a policy decision.

### Peak hours

**Peak = 18:00–22:59 local time**, i.e. `transaction_hour BETWEEN 18 AND 22`. Chosen because that is where transaction volume peaks in this dataset (38.6% of attempts in five of twenty-four hours), so it is the window where capacity pressure would show up. The bounds live in `config.py` as `PEAK_START_HOUR` / `PEAK_END_HOUR` and are injected into the SQL view.

### Incident window

**Crescent Bank, 10 March 2025 (inclusive) to 21 March 2025 (exclusive) — that is 10–20 March, eleven days — peak hours only.** This is engineered into the generator, so the analysis has a known ground truth to recover. The `incident_period` label (`Before` / `During` / `After`) is part of the SQL view; the comparison itself is in `sql/06_impact_prioritization.sql`.

Because the three windows differ in length (68 / 11 / 102 days), the incident table normalises to failures per day. Raw counts across unequal windows would be misleading.

### Amount bands

`Under INR 200`, `INR 200-999`, `INR 1,000-4,999`, `INR 5,000-9,999`, `INR 10,000+`, with an explicit `amount_band_order` column so they sort by value rather than alphabetically. Payment values are long-tailed by design (median far below the ₹688 mean), so the top band holds only 499 attempts and is flagged `low_sample_flag = 1`. It is displayed but no recommendation is built on it.

### Missing values

There are none, by design, with one deliberate exception: **`failure_reason` is blank on successful rows.** That is a semantic blank, not missing data. `validate_data.py` excludes that column from the completeness check and instead asserts the stronger property in both directions — every failed row has an allowed cause, and no successful row has one.

### Why both rates and absolute volumes are always shown

A rate tells you how bad something is for a customer who lands in that segment; a count tells you how much of the total problem it represents. They routinely disagree, and acting on the wrong one wastes engineering time:

| Segment | Success rate | Failures | Which one matters |
|---|---:|---:|---|
| 2G network | 92.44% (worst in dataset) | 407 | Worst experience, small pool |
| Bank Timeout (cause) | — | 2,195 | Largest addressable pool |
| INR 10,000+ band | 94.59% | 27 | Too small to act on |

Every scorecard in the SQL layer therefore carries `transactions`, `failures`, `success_rate` and a contribution share together, and `segment_performance` adds a low-sample flag.

## 3. Distinguishing signal from noise

Segment rates computed on different sample sizes are not directly comparable. `sql/04_segment_analysis.sql` computes a 95% normal-approximation confidence half-width per bank:

```sql
1.96 * sqrt(success_rate * (1 - success_rate) / transactions) AS success_rate_ci95_halfwidth
```

(`sqrt` is registered as a Python function on the SQLite connection in `run_analysis.py`, so the query works regardless of how the local SQLite was compiled.)

The result changed the conclusion. Bank success rates span 95.44%–95.72%, a **0.28 pp** spread, against a half-width reaching **±0.27 pp** on the smallest bank. The intervals overlap, so the six-month bank ranking is **not** a finding, and the lowest-ranked bank is not the bank that had the incident. The bank chart on the Executive Dashboard is drawn with error bars for exactly this reason.

The real bank finding required a three-way cut — bank × incident period × peak hours — where Crescent Bank moves 6.8 pp while a control group of every other bank moves 0.2 pp in the same hours, and then returns. That contrast is what makes it defensible.

## 4. Scenario model

The Impact Simulator converts a reduction in a measured failure pool into recovered transactions and value. Three levers act on **mutually exclusive** pools, so no transaction can be counted twice:

| Lever | Pool | Size |
|---|---|---:|
| Timeout reduction | Attempts with `failure_reason = 'Bank Timeout'` | 2,195 (avg ₹659.74) |
| Network reduction | Attempts with `failure_reason = 'Network Error'` | 1,771 (avg ₹727.13) |
| Retry recovery uplift | `final_retry_outcome = 'Still Failed'` **excluding** the two causes above | 978 (avg ₹666.18) |

```
recovered_transactions = timeout_failures × timeout_reduction
                       + network_failures × network_reduction
                       + retry_pool      × retry_uplift

recovered_value        = each pool × its rate × that pool's observed average failed value
success_rate_uplift_pp = recovered_transactions ÷ total_transactions × 100
```

Insufficient Funds and Risk Decline are excluded from the targeted causes on purpose: they are customer- and policy-side, not infrastructure the platform can engineer away.

The identical arithmetic exists in three places — `run_analysis.py` (for `summary.json`), the Excel formulas, and `tests/test_analysis_outputs.py` (which recomputes it independently). The Excel QA pass recalculates the workbook and compares the results back to `summary.json`.

**What the model excludes:** engineering cost, capacity and risk; customer re-attempt behaviour and substitution to another payment method; fraud and chargeback exposure from retrying more; interaction between the levers; any revenue attribution. Outputs are scenario estimates, not forecasts, and no stated impact has occurred.

## 5. Reporting layer

The Excel workbook is generated by `src/build_excel_dashboard.py` using **XlsxWriter**. Design rules:

- Every presentation figure is a **formula** referencing the Analysis Data sheet, which holds the exact CSV outputs. Nothing is typed twice, so the workbook cannot disagree with the analysis.
- Formulas are written **with their computed result cached**, so the file displays correct values in any viewer, not only after a recalculation.
- Charts read from named blocks on Analysis Data rather than duplicated copies of the same series.
- The weekly chart plots **complete weeks only** — the first and last reporting weeks are partial (5 days and 1 day) and would otherwise create a fake dip at both ends. Partial weeks stay in the table with an `is_complete_week` flag.
- No PivotTables, no macros, no 3D charts. Gridlines hidden, header panes frozen, print areas and landscape A4 page setup defined on every sheet.

### Implementation change, stated plainly

An earlier version of this builder targeted a proprietary JavaScript spreadsheet runtime available only inside a specific tooling sandbox, reached through a machine-specific dependency junction. That build also stalled during full-sheet rendering and never exported a workbook. It was replaced with XlsxWriter because **a portfolio project has to be rebuildable by anyone who clones it** — the previous dependency was `"private": true` and not installable from a public checkout. The workbook design, formulas, charts, validation and sheet order are unchanged in intent; only the library differs. Build time went from "did not complete" to about one second.

### Verification in Excel

`scripts/excel_qa.ps1` (Windows + Excel only) opens the workbook, forces `CalculateFullRebuild`, scans every sheet with `SpecialCells(xlCellTypeFormulas, xlErrors)` and `SpecialCells(xlCellTypeConstants, xlErrors)`, records 19 recalculated values, and exports a PNG of each sheet — growing the capture window to cover floating charts so clipping and chart-over-table overlaps are visible. **The workbook is never saved by this script**, so the committed file stays byte-identical to what the Python builder produced.

## 6. Testing

52 pytest checks in four groups:

1. **Generator** — determinism under a fixed seed, sensitivity to a different seed, schema, uniqueness, allowed values, status/reason consistency, retry consistency, plausible success-rate bounds, and that the engineered peak and incident patterns are recoverable from the data.
2. **Validation** — six deliberately corrupted datasets, each of which must be caught by the specific check that owns it.
3. **Reconciliation** — headline KPIs recomputed independently in pandas must equal the SQL outputs and `summary.json`; plus database row counts, Pareto contributions summing to 1, per-dimension contribution sums, the 7-day moving average, retry counts, mutually exclusive simulator pools, and scenario arithmetic.
4. **Workbook** — sheet names and order, zero error cells and zero error literals in the XML, KPI cards as cross-sheet formulas with correct cached values, editable and range-validated simulator inputs, safe-division output formulas, hidden gridlines, frozen panes.

The workbook tests read the `.xlsx` as a zip of XML using only the standard library. That is deliberate: it asserts on what is actually stored in the delivered file rather than on what a spreadsheet library reports.

## 7. Known limitations

- **Synthetic data.** Patterns were engineered to be recoverable. Real payment data has more confounding and would not produce this clean a Pareto.
- **Diagnosis, not causal inference.** The incident analysis is a difference-in-differences *style* comparison with a natural control group, not a controlled experiment.
- **Scenario estimates, not forecasts.** See section 4 for the full exclusion list.
- **Initial-attempt success rate.** Deliberate, and reported alongside retry recovery rather than blended.
- **Thin high-value segments.** 499 attempts above ₹10,000; flagged, not acted on.
- **Six months, one platform.** No seasonality beyond the window, no market or competitor context, no cost model.
- **Excel-locale rendering.** Number formats follow the viewer's locale, so digit grouping may appear as `1,80,000` in an Indian Excel and `180,000` elsewhere. The values are identical; only the grouping convention differs.
